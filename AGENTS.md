# Agent guide

This repo is a beginner path for model-railroad ESP32 boards that talk to JMRI/CATS over MQTT. Prefer the Board Configurator and the install scripts over hand-edited YAML.

## How to help

- Use plain language. One step at a time for setup and troubleshooting.
- Give the exact command for the person's OS (macOS Terminal, Windows PowerShell, or a Linux terminal), then say what success looks like.
- If something fails, give only the next check. Do not dump a long list.
- Do not suggest Docker unless the person already uses it and asks to keep it.
- Beginner YAML comes from the Board Configurator, with Wi-Fi and MQTT values written into the file. Do not revive a modular `secrets.yaml` / `my-first-board` beginner path — that was removed.
- Do not put real passwords in docs or commit a generated `board.yaml`.
- Keep YAML and script edits small. Match the style of the file you are changing, and say why it changed.
- Do not rename files unless asked.
- `AGENTS.md` is the source of truth for agents in this repo (there is no separate Copilot instructions file).

## Logic work in progress

- The Logic page (field logic and MSS Logic) is built on the long-lived branch `feature/logic`, following `docs/field-logic-implementation-plan.md`. Each work item has a GitHub issue (label `logic`, milestones R0–R5). Branch it off `feature/logic` as named in the issue and PR back into it. PRs into `feature/logic` do not auto-close issues, so close the issue when its PR merges.
- Change `logic.js` and `components/mr_logic/logic_core.cpp` (with `logic_table.cpp`, which resolves names once) together: each JS function has a counterpart, listed at the top of `logic_core.cpp`. CI replays the cases against both and feeds both the same random events (`engine` job in `test.yml`).
- The JS engine is `configurator/logic.js` (`EsphomeMrLogic.createEngine`, `explainMast`): plain JS with no DOM, so the C++ core can mirror it. `test/engine-run.test.js` replays every case against it. It is not loaded by `index.html` until a page part needs it (Try it, Explain).
- **Direction (approved 2026-11-26):** the Field Logic page is being rebuilt from scratch as [the track plan spec](docs/field-logic-plan-spec.md) describes: two kinds of building block, the drawing and your own pieces and rules, with no starters or named behaviours and nothing to add for protection. Work in the order of the *Track plan* milestone (TP 0-10). Until TP 9 the old page and the pieces below are still on the branch; do not extend the old page, its sections UI or starters. **Protection (amended 2026-11-27)** follows prototype interlocking: a controlled signal clears only for a route that has been asked for (Auto: the board, for a train heading through; Manual: CATS/JMRI unholding it, or its signal button) and set, and the route is released behind the train; see the spec's *Routes asked for, set and released*. Do not bring back inferring a request from a train standing at a signal, or the leaving guard, for the track plan.
- The track plan (`logic.plan`, Field Logic) is built, not stored, like MSS Logic: `configurator/plan-builder.js` (`EsphomeMrPlanBuilder.build`, `problems`) turns the drawing into blocks (with their neighbours, `next`), masts, groups, resources, signal buttons and crossover `pairs`, and `logic-yaml.js` `logicItems` puts them before the Logic page's own. Its cases (`test/cases/plan/`) give the drawing and a hand-worked timeline; `test/plan-cases.js` builds them, `test/plan-builder.test.js` replays them in JS and `test/engine-diff.test.js` in the C++ core. Loops made only of the plan's signals are allowed (`loopsThrough`); any other mast cycle is still an error. The editor is `logic-ui-plan.js` (part `logic-plan`: pure `layout` and `pick`, then the page) over `plan-edit.js` (pure changes that keep blocks, arrows and point settings with the track; `setSignalOptions` for a signal's button and Manual only); `test/plan-editor.test.js` redraws each plan case from an empty page. **Routes (TP 4)** are built, never chosen, and there are no sections: two routes clash when they share a piece of track (between turnouts, crossings, breaks and ends; a crossing is a piece of its own) unless a turnout must be set differently for each. A signal with a route that can clash is controlled; the rest are block signals. A controlled signal's routes are a routes group `<signal> moves` (`routes: true`), sharing one request: asked for in Auto by a train entering the block behind not from the block ahead (`notFrom`), in Manual by its mast going Held to Unheld or its button (each `if` the Auto/Manual switch), in Auto freed by time if its train never enters (the block behind clear for its hold time, else its Timing), in Manual cancelled by a hold or the button again, withdrawn when the switch flips (`withdraw`). Each route takes everything from its signal to its end, all at once: every piece of track a sensor sees (a piece of a block is taken with another of that block when every route using it uses that one too; unseen track is freed with the next seen block); each is freed behind the train once seen in the next block (`then.next`), each turnout is locked with the piece it leads into (`{ turnout, with }`), and the block behind's hold time is the route's `approachLock`. Clashing on track with no sensor of its own, no sensor just past a controlled signal, or nothing to ask in Auto or Manual, is an error. Crossovers found on the drawing are paired (a point's `pairedWith` changes it), and `generator.js` `emitPairedThrow` makes a command or button for one throw both. On the board: the `Auto` switch (MQTT `trains/track/light/auto/<board>`, JMRI `MLauto/<board>`, optional fascia toggle `plan.auto.pin`), each rule button on its pin and the web page, and `Release <signal>` per route in place of the pieces' releases. `look` gives the editor `protects`. Turnouts are also locked by the plan's locks group (under a train, track locking and approach locking). Rows waiting for an aspect the next signal cannot show are left out, and the checker does not report the plan's own rules as never applying (`mine` in `logic-checker.js`). **Checker on plans (TP 5):** a part too big to explore (a station's routes all share track) is checked from its routes' rules (`routeProblems`, `analysable`), and the builder's `endBlocks` tell it where the drawing ends: a head-on meeting with a train come in from beyond an end is not counted (decided 2026-11-27; the layout beyond holds it, or it is released by hand). `test/checker-plans.test.js` keeps that check equal to exploring every state, and `test/plan-station.js` is the 18-block station it must check completely. The switch (`auto`) and each route signal's JMRI hold (`hold<sep><mast>`) are inputs where the rules read them (TP 5b, #147); a waiting request freezes its own mode's inputs, the switch and its own signal's hold. `test/browser/plan-editor.mjs` drives the editor in Chromium (not in `npm test`). Aspects, approach lighting, the Advanced fold, the signal panel's button and Manual only, and problems marked on the drawing are not built yet.
- Engine cases (`configurator/test/cases/*.json`, format and scan rules in its `README.md`) are worked out by hand from the spec. When an engine fails one, fix the engine or raise the spec question; never regenerate a case from an engine's output. A multi-board case (`boards`) wires several engines by their plant ends through a small broker, the same in `test/engine-runner.js` and `engine-tests/main.cpp`. A plant end's link is never in the board's table, only in the engine's start and events.
- MSS Logic (`logic.mode: "mss"`) is built, not stored: `configurator/mss-builder.js` (`EsphomeMrMssBuilder.build`, `problems`) turns `logic.mss` into Field Logic blocks, masts, Block signals and Route signal groups (through the starters) and plant ends. `logic-yaml.js` reads every logic item through `logicItems(config)`, so an MSS board generates exactly as Field Logic does; its own validation runs first, and Field Logic's checks, the checker included, then run over the built items with each message pointed back at the description. MSS cases (`test/cases/mss/`) give the description and a hand-worked timeline; `test/mss-builder.test.js` builds and replays them.
- Do not merge logic work into `main` until Release 5 of the plan is complete. `main` (and the live configurator) stays as today until then.

## Install and MQTT

- Supported install: `scripts/install-mac.sh`, `scripts/install-windows.ps1`, or `scripts/install-linux.sh` only. One-liners are in `README.md`. Do not maintain a parallel hand-install guide.
- Windows install must set `RemoteSigned` for the current user, `Unblock-File` the downloaded `.ps1`, and elevate with `-ExecutionPolicy RemoteSigned` — never `Bypass`. Defender often false-positives `Bypass` and unsigned PowerShell installers; the script adds Defender exclusions for `%USERPROFILE%\esphome-mr-installers` and `%ProgramData%\esphome-mr`, and the failure guide covers Allow / Restore.
- Linux install is 64-bit Raspberry Pi OS (the usual Pi-SPROG machine), Debian, Ubuntu and relatives, Fedora and RHEL relatives, openSUSE, and Arch. It does not edit Pi boot files or the SPROG serial port. A 32-bit Pi needs the 64-bit image.
- ESPHome is the Device Builder desktop app at http://localhost:6052. The install script downloads the latest desktop app, then runs its updater so the builder inside it matches the current release. Config files live in `~/esphome` (Mac and Linux) or `%USERPROFILE%\esphome` (Windows).
- MQTT is Mosquitto on port **1883**, anonymous, on a trusted home LAN. Setup writes `listener 1883`, `allow_anonymous true`, and `persistence true` (retained messages survive a broker restart), then checks the service is running with auto-start.
- MQTTX is the GUI topic browser (not MQTT Explorer — Mac Gatekeeper breaks those builds). Connect to `127.0.0.1:1883` with no username to watch the local broker.
- After install, the script offers to open the Board Configurator in the browser (Enter to open, `n` to skip).
- The configurator defaults the MQTT broker to `layout-mqtt.local`. A typed-in LAN IP works in that field too. Never `localhost` / `127.0.0.1` in board YAML or JMRI.
- The install scripts publish `layout-mqtt.local` on the network. Preflight looks for that name first. If another computer already answers, the script warns and does not publish over it. `ping layout-mqtt.local` checks the computer that owns the name. On this computer, the name comes back after a reboot and is removed on uninstall.
- Generated YAML needs ESPHome **2026.9.0** or newer (`esp32: variant`, `ota` encryption, `min_version`).

## Board Configurator

- Live at https://aaron9589.github.io/esphome-for-model-railroading/
- Source: `configurator/` (static site). Deployed by `.github/workflows/pages.yml` on pushes to `main` that touch `configurator/**`, only after `.github/workflows/test.yml` passes; `configurator/test/` is left out of the site. `test.yml` also runs on PRs into `main`, `feature/logic` and `logic/**` (stacked work items) and on pushes to `feature/logic`.
- Writes one `board.yaml` with an `esphome-mr-config:1` comment so the same file can be imported again. Do not invent a second file format.
- New boards get a six-character name suffix (`board.nameSuffix`, letters and digits without `0`, `o`, `1`, `l`), kept on rename: it is the board's identity at a meet. The Board page edits the part before it (19 characters at most) and offers **Add a suffix** (old boards; the page's main button) and **New suffix** (a copy of another board's file; a button beside the suffix, which is shown as a tag, and asks first). A board without one writes exactly the old YAML.
- **Expanders (MCP23017)** on the Sensors page (`config.expanders`): each shares a PCA9685 board's SDA/SCL (`bus`, from 1) or has its own `sda`/`scl`; address `0x20`-`0x27`. A sensor on one stores `expander` (its name) and `pin` (0-15, shown A0-B7) instead of `gpio`. The page lists sensors on ESP pins first, then the Expanders section: each expander as a card with its sensors under it, with its own **Add sensor**. The Turnouts page has the same shape (`.boards-section`): turnouts on ESP pins, then the PCA9685 boards section: each board's card with its turnouts and **Remove board**, and **Add PCA9685** (buttons, as for expanders; there is no tick box). With no boards (`pca9685: false`), **Add PCA9685** moves the ESP-pin turnouts onto PCA9685 1; removing the last board moves them back to ESP pins. The header's **Add turnout** goes on PCA9685 1 when boards are in use. Each of Sensors, Turnouts and Signal Masts has a count line under its heading (`.pin-budget`): how many, and the pins (or PCA9685 channels) free. The Signal Masts page's CATS template note sits below the masts: it is for CATS, or the masts in the JMRI file. PCA9685 and expander cards fold from their title (`foldHeader`); which are folded is not saved. `i2cBuses()` works out the buses (two at most); one bus keeps the id-less `i2c:` YAML. Files without expanders keep no `expanders` key.
- **Logic page** (on `feature/logic` only, being built): stored in `config.logic` (`mode`, `share`, ...); the page is `logic-ui.js` plus one file per part (`logic-ui-masts.js`: Masts, Buttons; `logic-ui-rules.js`: Sections, Groups and the rule cards; `logic-ui-views.js`: Who uses what, the control table; `logic-ui-start.js`: starters, the Download page's Logic version). Each part calls `EsphomeMrLogicUi.registerPart({ id, order, modes, text, render })`; its id is its card's element id, which validation links point at. Every word is in a `TEXT` handed to `registerPart`, linted for spec-only terms. Parts keep their logic in pure functions on their global (tested without a DOM) and use the shared helpers in `EsphomeMrLogicUi.UI`. Starters (2.8) are in `logic-starters.js` (the core: `defineStarter`, `defaults`, `problems`, `build`, `apply`, `dialog`), with One-train section and Lock turnouts in `logic-starters-sections.js` and Block signals and Route signal in `logic-starters-signals.js`. Building is plain JS that Node tests call; each starter's worked example is checked by putting its rules into the matching engine case and replaying it (`test/starters-*.test.js`). A starter's form turns its card on through `EsphomeMrLogicUiStart.registerStarter`. **MSS page** (4.2): `logic-ui-mss-steps.js` (guided steps, Ends, the Signals grid), `logic-ui-mss-module.js` (the module picture `logic-mss-module`, pinned at the top: a pure `layout(config)` of ends, tracks and junctions, checked by `test/mss-module.test.js`, falling back to one track to a row when tracks would overlap; clicking a block or boundary opens its form, a junction or end scrolls to its card); Try it (`logic-try`, registered for both modes) draws it live in MSS Logic through `livePicture` (trains in blocks, each signal's lamp, the route the turnouts set, turnouts to click) and runs a train with `trainRoute` (in at an end, along the set route, out at another) and `trainStarts`; `EsphomeMrMssBuilder.namesOf` maps the description to the built block and signal names. It hides the signals with no lights and the Sections heading, `logic-ui-mss-tracks.js` (each track's From and To, and the form for the block or boundary picked on the picture, `pick`/`picked`; any change saves and draws the whole page), `logic-ui-mss-junctions.js` (junctions from a shape, routes; a junction keeps the `shape` it was made from, used only to draw it), `mss-templates.js` (the standard MSS modules: Crossover, Cascade, Complex cascade, as the ISE boards build them; `plan`/`apply` write the description and hand the page's `addItems` the sensors, turnout and CATS-aspect masts to add with free pins; signals are individual LEDs by default, three to a head, or one WS2812B LED a head with `style: "strip"`; the confirm panel warns when the LEDs outnumber `safeOutputPins`, the free pins that are not strapping pins; offered on the steps card while the module is empty), `logic-ui-mss-marks.js` (red dots: mark an element with `data-mss-part` and `data-mss-<key>` matching the builder's `where`; `apply` runs after the page draws). Parts register with `modes: ["mss"]` and the ids in `EsphomeMrMssBuilder.PARTS`; the views show built items read-only, marked Made by MSS Logic; `test/mss-page.test.js` lints MSS-only terms. Its YAML and XML come from `logic-yaml.js` hooks in `generator.js`. Mode None with Share unticked writes no `logic` key, so the YAML is unchanged. **Share with other boards** (on by default in Field Logic) adds only: the board Online topic as MQTT birth/will/shutdown, each sensor's retained `/State`, each turnout's retained `/Moving` (around announced throws, after `/Thrown`), each mast's retained `/State` (its JMRI aspect name), and the Owner MAC check (`trains/track/board/<board>/Owner`; a clash logs an error and shows on the web page). JMRI XML gets a Logic tick box with `MSboard/<board>/Online`. **Blocks** (`logic.blocks`, Field Logic only): each is a template `binary_sensor` `<block>_block`, occupied while any member is (this board's sensor by name, or `{board, sensor|block}` from a linked board, which reads occupied until known; a member on an expander that `is_failed()` or `status_has_warning()` reads occupied). It publishes like a detector, plus `/State` when sharing, and goes in the JMRI Logic box. **Field Logic on the board** (`logic-yaml.js`, work item 2.5): Field Logic always writes the `mr_logic` component (`external_components` from `LOGIC_COMPONENT_REF`, which CI checks exists on GitHub), the `Field logic` switch, a `Release <section>` button per section, and the `Logic version` text sensor. The rule table is the engine cases' board format (`logicTable`); the version code is a hash of it (`versionCode`). A mast that rules set keeps its `mqtt_subscribe` without `on_value` (the component reads it) and needs no MQTT. Aspect names in the table are the Signal Masts labels, in order, so they must be unique on masts logic uses. Untagged aspects are `stop`. A rule-locked turnout (`lockedTurnoutNames`) gets `<id>_field_locked` beside the remote lock in the button guard, `CLOSED`/`THROWN` handlers and latch script (`lockFlags`), and the lock report from a template `<id>_lock_report` even without Remote lock. With Field Logic the component runs the unlock re-sync (`remote_locked`, `resync` bindings), so the `UNLOCKED` handler only clears the flag. **Validation** (2.6): `validateConfig` returns `links`, a Map from each message to `{ view, part }` (a page, and an element id such as `logic-groups`); `renderMessages` adds a **Show** link. Logic checks live in `logic-yaml.js` `validate`, reported through `reporter(errors, warnings, links)`: references, aspects, sections (one per block, here and across linked boards, whose snapshot keeps `logic.resources`), the mast cycle check (`mastCycles`), rule-button pins, and the warnings. Messages say what is wrong, why, and what to do, in the page's plain words. **Checker** (2.9): `logic-checker.js` explores every reachable state of the rule table in the JS engine (replaying the shortest path to each state; a wait step runs scans until something changes, so each timer can elapse at any point; inputs are only what the rules read). It reports deadlock (an error, blocking the download), starvation, rules that never apply and masts stuck at Stop (warnings), and falls back to seeded random runs past its budget. Limits (4.5, spec *Checker limits*, re-measured with `configurator/test/bench/checker-limits.mjs`, which `npm test` does not run): it checks a board in parts (`partsOf`: a mast's or section's rules plus the masts they read), explores inputs the rules cannot tell apart once (`checkerInputs`; Try it keeps `inputsOf`), and keys a state on each section's waiting order (`checkerView().asked`). Any change to these must keep `test/checker.test.js`'s comparison with `{ split: false, allInputs: true }` passing. The checker branches from engine copies (`snapshot`, `restore`) and skips idle scans (`idleScans`, `skip`): checker-only in `logic.js`, with no C++ counterpart. `BUDGETS.validation` (2,000 states / 400 ms, then 200 ms of random runs) runs in validation in both Field Logic and MSS Logic, only when nothing else is wrong, memoised on the rule table; when it gives up, the Download page offers **Check every combination** (`checkFully`, `BUDGETS.full`: 30,000 states / 20 s), whose result stands until the rules change. Each link carries its Show me `sequence` (`{ do: event }` / `{ wait: scans }` after the start-up scan) for Try it. `logic.js` has `checkerView()` for it, with no C++ counterpart. **Try it** (2.10): `logic-try.js` is the pure core (`EsphomeMrLogicTry.createSession`: inputs from the checker's `inputsOf` plus "not known" for remote items, step, skip ahead, `play(sequence)` for Show me, `view()`; `shapesOf` for strip diagrams from One-train section and Block signals groups; `runTrain`), and `logic-ui-try.js` is the page part `logic-try` (order 88). A validation link with `sequence` opens it through `EsphomeMrLogicUiTry.showMe`. Renaming a sensor, turnout or mast on its page renames its Logic page references (`renameReferences`, on `change`, not per key, and not when another item of that kind has the old or new name). Deleting one leaves the references, which validation reports by name. Field Logic shows the Plant ends card (`logic-ui-ends.js`, `shown`) only for a board that already has ends; do not add a way to create them there.
- The mast editor lists lamps top of the mast first (with LED numbers; the stored `lamps` array stays LED 0 first) and shows each aspect as a card with a small mast picture; click a lamp to set its colour and effect. The raw JMRI match strings sit under a collapsed *JMRI aspect* section. There are no lamp presets.
- The UI calls the sections Sensors, Turnouts, and Signal Masts (the JMRI table names), with a JMRI badge in the nav. The stored keys stay `blocks`, `points`, and `signals` so old files import.
- Settings made on the running board's own web page (servo endpoints; the board-wide signal brightness, blink and pulse sliders) are explained in folded help beside the setting they belong to (`runningBoardHelp`: each turnout card, under each mast's Aspects), with the board's own `http://<name>.local`, not in page-wide notes.
- **Clear this page** (`CLEARS` in `app.js`): each page but Download has one in its header, which asks first in a panel under the header. Board goes back to a new board's settings but keeps the name suffix and the hotspot and API keys (and clears the saved Wi-Fi and MQTT); Sensors removes sensors and expanders; Turnouts removes turnouts and goes back to one PCA9685; Signal Masts removes the masts; Logic keeps only `mode` and `share`. References left behind on the Logic page show as problems.
- **Import** is a menu: *From a file* or *Paste from ESPHome* (a dialog; same parser, so it needs the `esphome-mr-config:1` header). **Send to ESPHome** on the Download page copies the YAML and opens http://localhost:6052 with paste steps. It does not write to the Device Builder directly: the Device Builder rejects other origins unless `ESPHOME_TRUSTED_DOMAINS` lists them, and the install scripts deliberately leave that unset.
- The Download page also offers **Download JMRI XML** (`generateJmriXml`): a `layout-config` file for PanelPro's *Load table content and panels*. The hardware address is the part of the topic after `track/sensor/`, `track/turnout/`, or `track/signalmast/`, giving `MS<address>`, `MT<address>`, and `IF$mqm:cats-masts:cats-virtual(<address>)`. Each turnout also brings `MS<turnout address>/Thrown` (its `ONESENSOR` feedback, `sensor1`) and, with Remote lock, `MS<turnout address>/Locked`. Tick boxes (Sensors, Turnouts, Signal Masts; all ticked on load, not saved) pick the tables; the turnout's own sensors go with Turnouts. CATS sets up its own sensors and turnouts, so CATS users tick only Signal Masts. Items whose topic lacks that type topic, and masts whose address has `(`, `)`, or `:`, are left out and listed. It validates against JMRI 5.4's `layout-4-19-2.xsd`. The page's first JMRI step is the MQTT connection: prefix `M`, Channel `trains/` (blank in new JMRI, `/trains/` before 5.1.2; both miss the board), and the default `track/<type>/{0}` topics.
- **v1 scope:** board settings (fallback hotspot and the ESPHome API included), block detectors, points on up to two PCA9685 boards (each on its own SDA/SCL pins, since a classic ESP32 has two I2C buses; points are listed under their board and store `pcaBoard`) or a few servos on ESP pins (those take power from the board, so 3-4 is the usual limit), optional panel buttons on those points, and signal masts. A mast is an ordered stack of lamps. Addressable mode is one WS2812B strip per mast, wired from the base so LED 0 is the lowest lamp, with that mast’s data pin. The strip length is the LEDs across the lamps. One lamp can be several LEDs that always light together, such as a three-LED route indicator. Each lamp is one of the layout colours (off, red `ff0000`, amber `ffc800`, green `1fff87`, white `ffffff`). Individual-LED mode is one GPIO per lamp, on or off. Either way a lit lamp is steady, hard blink, or pulse. Aspect names can come from `.jmri/resources/signals/cats-masts/`. The configurator embeds that folder as `configurator/cats-signal-template.zip`; unzip it into the JMRI profile so `resources/signals/cats-masts` is created, then restart JMRI. MQTT stays on unless Disable MQTT is ticked; that drops the broker and every JMRI topic, and the board will not talk to JMRI.
- The `cats-masts` template is for CATS (`~/Repos/cats-src`, `src/cats/layout/AspectMap.java`). CATS finds a JMRI mast by the CATS signal's name and calls `setAspect` with its default appearance keys, which are these 30 aspect names; with a template's HOLD_ONLY option it calls `setHeld` instead, and with approach lighting it calls `setLit(false)`. Each aspect's title, `speed`, and `speed2` come from CATS `IndicationNames` and `AspectMap.Speed`. Held and danger show R292, permissive R291. On the board, each mast's `mqtt_subscribe` handler is one lambda: an exact match on an aspect's strings wins; otherwise `Unlit` sets the aspect global to -2 (the show script's dark branch), `Held` picks the aspect named `R292` or `Stop` (else -2), and anything else matches on the aspect name before the first `;`. An unknown aspect is ignored. Both XML files validate against JMRI 5.4's `aspecttable.xsd` and `appearancetable.xsd`. Rebuild `configurator/cats-signal-template.zip` from `.jmri/` when they change.
- Default MQTT topics: `trains/track/sensor/<name>`, `trains/track/turnout/<name>`, and `trains/track/signalmast/<name>`; position feedback is the sensor `trains/track/sensor/<turnout>/Thrown` (`thrownTopic`: `ACTIVE` thrown, `INACTIVE` closed), which the JMRI XML sets as the turnout's `ONESENSOR` feedback. JMRI reads turnout feedback on its turnout receive topic, which by default is the command topic, so a nested `/State` was never heard. A point can opt into `<turnout-topic>/Lock`.
- Detectors publish with `retain: false` on purpose (avoid stale OCCUPIED in JMRI). Servo endpoint sliders, and the board-wide `Signal -` brightness, blink brightness/on/off, and pulse brightness, rate, and gap sliders, use `restore_value: true` on the ESP. Turnout position is the same kind of value: a `restore_value: true` bool. Changing it calls `update()` and `global_preferences->sync()` immediately, because the usual flash flush is about once a minute and a power cut was forgetting the position. On boot the servo moves to that saved position and does not publish. With more than one servo, each waits a random 0.2-1s first so they do not all start together. MQTT connect publishes `/Thrown` from the same bool with `retain: true` and QoS 2, as does each throw that came from a command or button. Nothing saved yet means normal, so the publish is `INACTIVE`. A sensor on a turnout's `/Thrown` or `/Locked` topic is a validation error. One aspect per mast can be marked to show at startup.
- Fascia buttons on a point are ignored while either of that point's throw scripts is running (`script.is_running` on `throw_closed` and `throw_thrown`). That covers the move to the endpoint, the 2s wait, and the backoff write. A second press in that window must not start the other throw, or the late backoff write leaves the servo short of the end it was sent to.
- A point control is momentary (`toggle`, `closed`, `thrown`) or latched (`latch-thrown`, `latch-closed`; on = pin pulled to GND). A latched control is not ignored while a throw runs. Its `on_state` runs a `queued` `${id}_latch_<n>` script that waits until both throw scripts have finished, then makes the point match the switch, so the switch and point cannot drift apart. On boot that script runs with `force: true` in place of the saved-position move, so the switch wins. A remote lock keeps the point where it is. At most one latched control per point (validation error).
- Optional per point: `lockEnabled` and `lockDefault` (`locked` or `unlocked`). With MQTT on, the board subscribes to `<turnout-topic>/Lock`. `LOCKED` sets `${id}_locked` (`restore_value: false`) and `UNLOCKED` clears it. While set, fascia buttons and `CLOSED`/`THROWN` are ignored. When `UNLOCKED` clears a lock that was set, a point with a latched control runs its `${id}_latch_<n>` script (`force: false`) so the point catches up with a switch moved while locked; a repeated or retained `UNLOCKED` does nothing. Boot still moves the servo to the saved position. `lockDefault` is the global's `initial_value` and is not kept across a reboot; a retained lock message replaces it when the broker connects. No lock global is emitted when the option is off or MQTT is off.
- Lock report (`lockedTopic`): a locked-capable point publishes `ACTIVE` / `INACTIVE` (retained, QoS 2) from `${id}_locked` to the turnout topic with `track/turnout/` swapped for `track/sensor/`, plus `/Locked` (`<topic>/Locked` if the topic has no `track/turnout/`). It is sent on MQTT connect and after every `LOCKED` / `UNLOCKED`. The JMRI XML adds it as sensor `MS<address>/Locked`, for CATS's *Turnout Locked Report*. A sensor on that topic is a validation error.
- When changing generator behaviour, update `configurator/test/generator.test.js` (or the feature's own `configurator/test/<feature>.test.js`, which `npm test` also runs) and run the configurator tests (`configurator/package.json`).
- `configurator/test/golden/` holds the YAML and JMRI XML for each board in `configurator/test/fixtures/`, byte-for-byte. A change that alters generated output fails them; if the change is meant, run `UPDATE_GOLDEN=1 npm test` and say why in the PR, which needs a reviewer's sign-off. The fixtures use fake credentials.

## When something fails, check in this order

1. ESPHome Device Builder is running (http://localhost:6052).
2. Mosquitto is running and listening on 1883, not localhost-only (`listener 1883` and `allow_anonymous true`); persistence and auto-start should already be set by the install script.
3. Nothing else owns ports 1883 or 6052.
4. USB cable, driver, and Chrome or Edge for the first flash.
5. Wi-Fi is 2.4 GHz with DHCP.
6. The broker is `layout-mqtt.local` (or the LAN address from `ping layout-mqtt.local`), and the firewall allows inbound TCP 1883.
7. For MQTT watching: MQTTX (or `mosquitto_sub`) on `127.0.0.1:1883`, subscribe to `#`.
